# 開発ストアから本番までの手順（案A: Shopify ペイメント）

担当の目安: 【院】= 先生が Shopify / FileMaker / Dokku の管理画面で行う、【開発】= 連携サービス・テーマのコード（Claude が作成）。
各ステップの末尾の「確認」が済んだら次へ進みます。

## フェーズ 1: 開発ストアの土台【院】

1. **基本設定**: 設定 → 一般（店舗名、住所、通貨 JPY、タイムゾーン Asia/Tokyo）。設定 → 税金（消費税、税込価格表示）。
   確認: 設定 → 一般に「iida-eye-shop-dev.myshopify.com」と日本の住所が入っている。
2. **テスト決済**: 設定 → 決済 → 「(for testing) Bogus Gateway」を有効化。Shopify ペイメントの申請は本番ストアで行う。
   確認: テスト注文でカード番号「1」が承認、「2」が拒否になる。
3. **顧客アカウント**: 設定 → 顧客アカウント → 「新しい顧客アカウント」（メールのワンタイムコード）を選択。「チェックアウト前にログインを求める」を有効化。
   確認: ストアの「ログイン」からメールにコードが届く。
4. **パスワード保護**: オンラインストア → 各種設定 → 「パスワードでアクセスを制限」は本番公開まで有効のままにする。
5. **商品登録**: コンタクトレンズは「製品 × 1 箱」を 1 商品として登録。SKU = FileMaker の `product_code`、商品タイプ「コンタクトレンズ」、タグ `rx-required`、「在庫を追跡」はオフ。アイケア用品はタグなしで登録。
   確認: 商品一覧で SKU が CL_Product と一致している。
6. **受取方法**: 設定 → 配送と配達 → 「店舗受取」を有効化（受取場所＝当院）。自宅発送は保健所の回答が出るまで配送料金を作らない。
   確認: チェックアウトで受取方法に「店舗受取」だけが出る。
7. **顧客メタフィールドの定義**: 設定 → カスタムデータ → 顧客 → 定義を追加。
   - 名前空間とキー `iec.rx_lines`、タイプ「JSON」
   - 名前空間とキー `iec.patient_id`、タイプ「1 行のテキスト」
   どちらも「ストアフロントのアクセス」を許可（テーマから読むため）。
   確認: 顧客の詳細画面にメタフィールド欄が 2 つ出る。
8. **カスタムアプリ**: 設定 → アプリと販売チャネル → アプリを開発 → 「カスタムアプリを作成」（名前: iec-ec-bridge）。
   Admin API スコープ: `read_orders`, `write_orders`, `read_customers`, `write_customers`, `read_products`。
   インストール後に表示される **Admin API アクセストークン**（1 回しか表示されない）を控える。チャットには貼らない。
   確認: トークンが `shpat_` で始まる。
9. **Webhook**: 設定 → 通知 → Webhook → 「Webhook を作成」を 2 つ。形式 JSON、API バージョンは最新の安定版。
   - イベント「注文作成」→ `https://<連携サービスのドメイン>/webhooks/shopify/orders-create`
   - イベント「注文キャンセル」→ `https://<連携サービスのドメイン>/webhooks/shopify/orders-cancelled`
   同じ画面の下部に表示される **署名キー** を控える（`SHOPIFY_WEBHOOK_SECRET`）。
   確認: 2 件の Webhook が一覧に出る（URL は連携サービス配置後に設定してもよい）。

## フェーズ 2: 連携サービスの配置【院＋開発】

10. **FileMaker**【院】: FileMaker 定義書のとおり `Helm_cData.fmp12` に CL_ 4 テーブル、`api_` 5 レイアウト、`ec_bridge` アカウントを作成。テスト患者 1 名分の CL_Product / CL_Rx / CL_RxLine を入力。
    確認: 定義書「作成後の確認」のチェック 5 項目。
11. **Dokku**【院】: `docs/deploy.md` のとおりアプリと PostgreSQL を作成し、環境変数を設定（Shopify のトークン・署名キー、FileMaker の接続情報、`API_SHARED_KEY`）。
    確認: `https://<ドメイン>/healthz` が `{"status":"ok"}` を返す。
12. **Webhook の URL を確定**【院】: ステップ 9 の URL を実際のドメインに直す。
13. **通し確認（Webhook 模擬）**【開発】: `scripts/send_test_webhook.py` で署名付きの注文を送り、FileMaker の CL_Dispense に `verified` が入ること、規格を変えると注文が拒否されることを確認。
14. **通し確認（実注文）**【院＋開発】: `/api/members/register` でテスト患者を登録 → 顧客が作られメタフィールドに処方が入る → 開発ストアでログインし、テーマ改修前は管理画面の「注文を作成」で明細プロパティ `_rx_line_id` と規格を手入力して注文 → 交付記録ができる。
    確認: 管理画面 `/admin/` の Order verifications に `ok` が並ぶ。

## フェーズ 3: テーマ【開発】

15. **テーマの選定と取り込み**: 無料テーマ Dawn をベースにし、Shopify CLI でコードを取り込んでリポジトリの `theme/` で管理する。
16. **会員制**: 未ログインでは商品・価格・コレクションを一切表示せずログイン画面へ誘導。ログイン済みでも `iec.patient_id` のない顧客には「当院で会員登録が必要です」だけを表示。
17. **「あなたの処方レンズ」ページ**: `iec.rx_lines` を読み、左右それぞれの製品・規格・残り購入可能箱数・有効期限を表示。「カートに入れる」で `_rx_line_id` と規格を明細プロパティに付ける。CL 商品ページからの直接購入は無効化。
18. **技術未確定 3 点の確定**: チェックアウト時に注文を止められるか（止められなければ「注文直後の自動照合と自動キャンセル」を正式方式にする）、テーマからメタフィールドを読めるか、ストア側の新規登録を閉じられるか。結果を計画書の開発仕様タブに記録。
19. **シナリオ検証**: 開発仕様のテストシナリオ 1〜15 を、テスト患者データと Bogus Gateway で実施。

## フェーズ 4: 周辺機能【開発、一部院】

20. **LIFF に会員登録画面**: メール入力、院外購入可の説明と同意 → `/api/members/register`。
21. **LINE 通知**: 注文受付、自動キャンセルの理由と受診案内、入荷（受取可能）の 3 種。Messaging API のチャネルアクセストークンは Dokku の環境変数へ。
22. **FileMaker スクリプト**【院】: 「CL_処方を確定」から `/api/rx/refresh`、「CL_入荷済みにする」から入荷通知の呼び出し。
23. **領収証**: 保険診療と区別した領収証を注文確認メールからダウンロードできるようにする。
24. **自施設交付割合の集計**: 施設基準の届出（様式 30）向けに、CL_Dispense（trial を除く）と Helm のコンタクトレンズ検査の患者数から算出。

## フェーズ 5: 本番ストアへ【院＋開発】

25. 本番ストアで 1〜9 を再実施（テーマ・商品は開発ストアから複製）。本番用のカスタムアプリ・Webhook・トークンは別に作り、Dokku の環境変数を本番値に切り替える。
26. **Shopify ペイメントの申請**: コンタクトレンズ（高度管理医療機器）を診察済み患者に交付する会員制ストアであることを説明し、取扱可否を確認。
27. **法定表示**: 特定商取引法に基づく表記、プライバシーポリシー（診療情報を購入可否の判定に使う旨）、利用規約、返品条件。
28. **ドメイン**: `shop.iida-eye.jp` を接続し SSL を確認。
29. **公開前の最終確認**: 未ログインで商品 URL に直接アクセスしても何も見えないこと（シナリオ 12）、検索エンジンにインデックスされない設定、パスワード保護の解除。
30. **開店**: まずアイケア用品のみで開店し、保健所・厚生局の回答とメーカー・卸の対応確認が済んでからコンタクトレンズを追加。
